TABLE type_conge
----------------

code                     VARCHAR(30), obligatoire, unique, en majuscules
libelle                  VARCHAR(120), obligatoire
description              TEXT, facultatif
actif                    BOOLEAN, defaut TRUE

mode_decompte            VARCHAR(30), facultatif

Regle metier : un type deja utilise n'est pas supprime. Il est desactive.

id                         BIGINT IDENTITY, cle primaire

type_conge_id              BIGINT, FK type_conge(id), RESTRICT
demande_conge_id           BIGINT, liaison facultative avec C

date_fin                   DATE, obligatoire

commentaire                TEXT, facultatif

justificatif_nom_stocke    VARCHAR(255)

statut                     VARCHAR(30), defaut ENREGISTREE

modifie_le                 TIMESTAMP, defaut CURRENT_TIMESTAMP

writable/uploads/absences

5. CLES ETRANGERES CONDITIONNELLES AVEC B ET C
======================================================================

- anomalie_pointage.planning_id -> planning_travail.id
- anomalie_pointage.pointage_id -> pointage.id
- absence.demande_conge_id -> demande_conge.id

Ces cles sont ajoutees seulement lorsque les tables correspondantes existent.
Elles sont creees NOT VALID afin de ne pas bloquer d'anciennes donnees, tout en
protegeant immediatement les nouvelles ecritures.

Si B ou C cree ses tables apres la migration D, executer ensuite :
database/partie_d/complete_foreign_keys.sql

Ce script est idempotent et ne supprime aucune donnee.


======================================================================
5 BIS. POINT DE COORDINATION AVEC LA PARTIE C FUSIONNEE DANS MAIN
======================================================================

La partie C a ete fusionnee dans main apres D et fournit egalement une
definition de type_conge dans database/bloc7/partie_c.sql.

Differences a harmoniser avant execution sur la base partagee :

Partie D                         Partie C
mode_decompte                    unite_decompte
justificatif_obligatoire         justificatif_requis
modifie_le                       colonne absente dans le script C
cree_par / modifie_par           colonnes absentes dans le script C
JOURS_OUVRES                     jours_ouvres
JOURS_OUVRABLES                  valeur non prevue par C
JOURS_CALENDAIRES                valeur non prevue par C
A_DEFINIR                        valeur non prevue par C

Le CREATE TABLE IF NOT EXISTS de chaque module ne complete pas automatiquement
une table creee par l'autre module. La migration D detecte cette incompatibilite
et s'arrete sans modification destructive si les colonnes requises manquent.

Decision requise de l'equipe avant de deployer les scripts sur la base partagee :
1. choisir un nom canonique pour les colonnes de decompte et de justificatif ;
2. creer une migration d'harmonisation conservant les donnees existantes ;
3. adapter ensemble les Models et Services C/D au schema canonique ;
4. ne pas executer aveuglement les deux definitions type_conge dans un ordre
   quelconque ;
5. tester la migration d'harmonisation sur une copie ou un schema isole.

La table demande_conge de C utilise le statut approuvee. Le service D le reconnait
correctement apres normalisation en majuscules (APPROUVEE).

6. WORKFLOW - ANOMALIES DE POINTAGE
======================================================================

1. Un utilisateur RH/Admin ouvre /bloc6/anomalies.
2. Il choisit une periode et, si necessaire, un salarie, un departement,
   un type ou un statut.
3. La detection lit planning_travail et pointage.
4. Le service ignore les jours de repos.
5. Une journee sans pointage n'est detectee qu'apres la fin planifiee.
6. Les anomalies detectables sont : entree sans sortie, sortie sans entree,
   journee terminee sans pointage, retard, heures incoherentes et ecart a
   verifier.
7. Un retard reste identifie comme RETARD et n'est pas automatiquement traite
   comme une erreur de pointage.
8. La contrainte unique empeche la creation d'un doublon lors d'une nouvelle
   detection. La date de derniere detection est actualisee.
9. Le RH ouvre la fiche de l'anomalie et choisit EN_COURS, REGULARISEE ou
   IGNOREE.
10. Un motif est obligatoire pour REGULARISEE et IGNOREE.
11. Le statut, le motif, l'auteur et la date sont enregistres.
12. Le changement est ajoute dans anomalie_pointage_historique.
13. Une regularisation ne modifie jamais silencieusement le pointage de B.


======================================================================
7. WORKFLOW - TEMPS REELLEMENT TRAVAILLE
======================================================================

1. L'utilisateur ouvre /bloc6/temps-travaille.
2. Il filtre par periode, salarie ou departement.
3. Le service rapproche employe, planning_travail et pointage.
4. Pour chaque jour planifie non repose :
   - les heures prevues viennent du planning ;
   - les heures realisees sont calculees seulement si entree et sortie existent ;
   - temps net = sortie - entree - pause ;
   - une sortie avant l'entree est interpretee comme un passage de minuit ;
   - une sortie manquante ne produit aucune journee complete fictive ;
   - la pause n'est soustraite qu'une seule fois ;
   - le retard et les heures supplementaires restent coherents avec B.
5. La synthese affiche : heures prevues, heures travaillees, ecart, retards,
   heures supplementaires, jours incomplets, jours planifies et jours pointes.
6. Aucune donnee n'est transferee automatiquement vers la paie.


======================================================================
8. WORKFLOW - ABSENCES ET JUSTIFICATIFS
======================================================================

1. Un RH/Admin ouvre /bloc7/absences.
2. Il filtre ou consulte la liste des absences.
3. Lors d'une creation/modification, le serveur controle :
   - l'existence du salarie ;
   - la validite de la periode ;
   - l'absence de chevauchement incompatible ;
   - l'existence du type selectionne ;
   - le justificatif obligatoire selon le type ;
   - la coherence d'une demande de conge liee, si C est disponible.
4. Une simple absence ne cree jamais un conge approuve et ne modifie jamais
   un solde de conge.
5. Le justificatif est controle cote serveur : taille, extension, type MIME et
   nom de stockage aleatoire.
6. Le fichier est place hors du webroot.
7. L'absence et son historique sont enregistres dans une transaction.
8. Si la validation ou l'ecriture SQL echoue, le nouveau fichier est supprime.
9. En cas de remplacement reussi, l'ancien fichier est supprime seulement
   apres validation de la transaction.
10. Le telechargement passe par un controle d'autorisation cote serveur.


======================================================================
9. WORKFLOW - TYPES DE CONGE
======================================================================

1. Un RH/Admin ouvre /bloc7/types-conges.
2. Il recherche, cree ou modifie un type.
3. Le code est normalise en majuscules et doit etre unique.
4. Le libelle est obligatoire.
5. Le justificatif obligatoire et le mode de decompte sont configurables.
6. Aucun droit legal ou taux d'acquisition n'est fixe arbitrairement.
7. Un type utilise dans une absence ou une demande de conge n'est pas supprime.
8. Le type est desactive avec actif = FALSE.
9. Le referentiel reste reutilisable par la partie C.

10. SECURITE ET AUTORISATIONS
======================================================================

- Authentification obligatoire via le filtre auth.
- Controle metier via le filtre partied.
- Ecritures reservees aux roles RH et Administrateur.
- Protection CSRF sur les requetes POST.
- Autorisations controlees cote serveur, pas seulement dans l'interface.
- Requetes executees via les Models ou le Query Builder CodeIgniter.
- Justificatifs stockes hors du repertoire public.
- Aucun journal d'audit global n'est ajoute ; seules les traces metier D sont
  conservees.

11. MIGRATION ET DEPLOIEMENT
======================================================================

Migration :
app/Database/Migrations/2026-11-08-120000_CreatePartieDTables.php

Regles :
- PostgreSQL obligatoire.
- Verification de compatibilite avant modification d'une table D existante.
- CREATE TABLE/INDEX avec IF NOT EXISTS lorsque pertinent.
- down() refuse les suppressions automatiques pour proteger les donnees
  partagees avec B et C.
- aucune migration destructive ne doit etre lancee sur la base partagee.

Ordre conseille :
1. Installer les tables de B : planning_travail et pointage.
2. Executer la migration D.
3. Integrer les tables de C lorsqu'elles sont stabilisees.
4. Executer complete_foreign_keys.sql si B/C ont ete installes apres D.
5. Auditer les anciennes donnees avant de valider les contraintes NOT VALID.
